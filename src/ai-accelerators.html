The research question

Evaluating the stack, not only the silicon

A model's numerical behaviour and execution speed are shaped by more than the device running it. Framework implementations, operator semantics, memory movement, preprocessing and runtime configuration all influence the result. This investigation compares four complete software and hardware environments under closely matched task protocols, distinguishing what can be reproduced from what varies in practice.

01 / Consistency

Does a shared starting point produce comparable training trajectories and generated responses?

02 / Performance

How do observed throughput and total runtime vary across frameworks and devices?

Why framework equivalence takes work

Matched model names are not enough for a meaningful cross-stack experiment. The evaluation addressed weight conversion, operator semantics, deterministic ordering and data-pipeline differences.

01 / Initialisation

Shared model state

The torchvision checkpoint was mapped into MindSpore parameter names with 267 of 267 parameters covered.

02 / Execution semantics

Comparable operations

TF32 defaults, pooling behaviour and batch-normalisation details required attention before outcomes could be compared.

03 / Provenance

Verified inputs

SHA-256 checks confirmed matching weights, splits, prompts, image manifests and Qwen checkpoint data for PyTorch T4 and reference inputs.

Offline .om compilation

Final atc compilation did not complete with the tested toolchain. The report records failures in the MindIR, AIR and ONNX compilation paths.

Model export is distinct from successful compilation and execution as a deployment artefact.

Interpretation

Comparable model outcomes can coexist with very different runtime performance.

Shared inputs produced closely aligned training trajectories and reported decoded-text agreement. Throughput varied with accelerator, framework and measurement path. These findings concern the tested stacks, not a universal device ranking or clinical diagnostic performance.
